Can Prior-Window Signals Improve Content Refresh Prioritisation?

A leakage-aware, client-held-out evaluation of a review queue for potentially declining content pages.

By Umer SajidRefresh / Content Opportunity Scoring lane12 August 2026
AbstractProblemDataMethodResultsLimitationsRecommendationsReproduceCredit

Abstract

This capstone asks whether an SEO or content editor can use page context and prior-month signals to prioritise a review queue for potentially declining content. It uses the bundled anonymised FlyRank ML Internship starter release, a 30,000-page snapshot across 32 pseudonymised clients, and evaluates transfer on seven entirely held-out clients. A leakage-aware random-forest model uses only stable or prior-window signals and is compared with a transparent visibility, freshness, and content-thinness baseline on the same test split. The model achieved Precision@50 = 0.540 versus 0.340 for the baseline, although the held-out decline base rate of 0.511 means this is a modest prioritisation result rather than an automated-action threshold. The output is a ranked review-for-refresh queue for directional decision support, not a causal estimate, a guarantee of traffic recovery, or a claim about Google’s algorithm.

1. Introduction and problem statement

Content teams often have more ageing pages than they can review in one editorial cycle. This capstone supports a single operational decision: which pages should an editor investigate first when refresh capacity is limited? The unit of analysis is one pseudonymised content page, and the output is a ranked review queue rather than an automated intervention. A false positive spends editorial capacity; a false negative leaves a potentially declining page outside the first review batch.

The target is an observed current-snapshot decline proxy: trend_direction == "down". In the starter release, that means impressions in the most recent 30 days are more than 20% below the preceding 30 days. The primary score is Precision@50 on clients unseen during training, reported with the test-set prevalence so the result remains interpretable.

2. Data and public-safety boundary

The analysis uses only the repository’s bundled anonymised starter release: data/raw/content_refresh_anonymized.csv. It is one denormalised snapshot table with 30,000 content-page rows, 44 columns, and 32 pseudonymised clients. All activity totals cover a trailing 90-day export window; *_prev_30d is days 31–60 before export and *_last_30d is the most recent 30 days. This capstone does not use the separate full warehouse release or raw client exports. See the data dictionary.

3. Methodology

The approach assumes that prior visibility, freshness, content age, content characteristics, and safe search context can help triage pages for review. It does not assume that those signals cause a decline or that a refresh will restore traffic. Numeric features include search-volume context, competition, CPC, content length, log prior-month impressions/clicks/sessions, content age, and days since last update. Categorical features include competition level, content type, main intent, and age, freshness, and length tiers.

The grouped split contains 23,837 training rows from 25 clients and 6,163 held-out rows from seven clients. This tests transfer to clients not observed during fitting rather than simple within-client pattern recovery.

4. Results

Permutation importance on held-out clients shows that prior-month impressions contribute the most measured discrimination: permuting log_impressions_prev_30d reduces ROC-AUC by about 0.141. Prior-month clicks, content age, and prior-month sessions make much smaller incremental contributions. This measures model dependence in this split; it does not identify a causal mechanism of decline.

5. Limitations and honest framing

Interpret with care. The held-out decline base rate is 0.511, so model Precision@50 of 0.540 is only modestly above prevalence even though it improves substantially on the selected transparent baseline. The model identifies pages for review, not pages guaranteed to benefit from a refresh.
  • The label describes an observed movement within a snapshot; it is not a future traffic forecast.
  • The analysis cannot show that refreshing a page causes traffic to recover; that requires a controlled intervention or causal design.
  • One grouped client holdout is a transfer check, not a complete multi-period or time-aware validation programme.
  • Permutation importance is associative rather than causal and describes this specific evaluation split.

6. Ranked recommendations and action playbook

The model creates a local ranked queue with a model score, baseline score, and non-label reason codes. To keep this public paper safe, page-level IDs and the ranked queue file are not published. The score is used to determine review order; it never triggers an automatic refresh.

StepEditor actionDecision boundary
1. TriageStart with the first 50 pages ranked for review for refreshRank is a queue position, not an editing instruction
2. DiagnoseCheck intent, factual currency, query coverage, on-page quality, and technical contextConfirm an actionable issue before changing content
3. Choose actionRefresh, expand, rewrite, monitor, or defer according to the diagnosisNot every observed decline needs a refresh
4. Record outcomeLog the decision and observe later performanceA time-aware or intervention study is needed to measure impact

The next research extension should use a forward outcome window from the full warehouse with time-aware validation to test subsequent decline rather than characterising the current snapshot.
